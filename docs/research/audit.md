# Аудит текущего «жидкого стекла» сайт-пример

Дата: 30.10.2026. Что смотрел: `<сайт>/assets/glass.js`, блок «Жидкое стекло» и соседние правила в `assets/page.css`, `src/glass-lab.html`, слайды первого экрана в `assets/site.js`. Сайт не менял.

Пометки:
- **[замер Chrome]** — измерено здесь, в Google Chrome 1440×900, DPR 2, через playwright-core. Скрипты лежат в `glass-rnd/research/tools/audit-*.mjs`.
- **[из кода]** — видно по исходникам, запуск не нужен.
- **[гипотеза, проверить в Safari]** — вывод по коду и чужим источникам. В настоящем Safari не проверено. Playwright-WebKit для этого не годится (см. CONTEXT.md).

## Коротко

1. **Шапка тормозит в Safari из-за самого устройства схемы, а не из-за настроек.** При каждой прокрутке копия под стеклом сдвигается, и фильтр из 17 шагов пересчитывается целиком, вместе с картой изгиба. А карта зависит только от формы капсулы и между кадрами не меняется. По чужим замерам WebKit и Gecko считают такие фильтры на процессоре. Площадь фильтра шапки при DPR 2 около 3450×240 ≈ 0,83 Мпикс, на каждом из 17 шагов, и так каждый кадр.
2. **Область фильтра лишняя на 27 %.** `x=-0.2 width=1.4` для капсулы шириной 1232 px даёт по 246 px пустого поля с каждой стороны, а для изгиба хватает примерно 3×rim ≈ 14 px. Доли можно считать в JS под размер элемента (Safari понимает доли, но не пиксели).
3. **Самая дорогая часть в WebKit — `feComposite arithmetic`.** У нас их 4 на кадр. Автор Glass-HQ/liquid-glass пишет, что в WebKit арифметический composite считается программно и занимал больше половины времени фильтра. Каналы R, G и B собираются без него, через `feBlend mode="screen"` или `lighten`: в каждом слое ненулевой только один канал, и результат получается тем же.
4. **Рывок при смене слайда виден и с матовым стеклом, то есть дело не в стекле** [замер Chrome]. Длинные кадры 69–169 мс без JS-скриптов внутри — это декодирование 2000-пиксельного webp в первом кадре. `show()` проверяет `img.complete`, но не ждёт `img.decode()`.
5. **Все 6 слайдов первого экрана (≈ 580 КБ) грузятся сразу** [замер Chrome]. `loading="lazy"` у них не работает: картинки лежат стопкой в видимой области (opacity 0, но в viewport).
6. **`glass.js` ломает ленивую загрузку постеров видео.** Копия под кнопкой ▶ делается с `removeAttribute('loading')`, поэтому постеры грузятся на 70-й миллисекунде, даже если видео внизу страницы [замер Chrome].
7. **Проверка `prefers-reduced-transparency` в Safari и Firefox ничего не делает:** по caniuse медиазапрос есть только в Chromium. Пользователь Safari с включённым «Уменьшить прозрачность» всё равно получит стекло.
8. **Кроссфейд 900 мс внутри линзы рискован в Safari.** Анимация `opacity` может вынести слой копии в отдельный композитный слой. Тогда либо пропадёт преломление (как было с `translate3d`), либо фильтр будет пересчитываться все 900 мс [гипотеза, проверить в Safari].

## Как мерил и что получилось (только Chromium)

| Режим | Прокрутка: средний кадр / p95 / худший | 8 с простоя со сменой слайда: худший кадр, кадров > 20 мс |
|---|---|---|
| frost, CPU ×1 | 8,3 / 10 / 10 мс | 109 мс, 6 |
| liquid, CPU ×1 | 8,5 / 10,1 / 17,7 мс | 116 мс, 5 |
| frost, CPU ×4 | 8,3 / 10,1 / 10,3 мс | 26 мс, 1 |
| liquid, CPU ×4 | 8,4 / 9,9 / 18,6 мс | 25 мс, 2 |

Long Animation Frames около смены слайда (19,5 с, три смены): frost — один кадр 169 мс; liquid — 88, 94 (старт) и 69 мс. Скриптов внутри длинных кадров нет, так что время уходит на декодирование и растеризацию.

Выводы:
- В Chrome жидкое стекло при прокрутке почти бесплатно (худший кадр 18 мс против 10 мс у матового). Значит, тормоза в Safari — это особенность WebKit (процессорный путь фильтров), а не ошибка в нашем JS.
- Мерить надо в настоящем Safari и на iPhone. Готовый способ: тот же цикл `requestAnimationFrame` + `scrollTo` из `audit-bench.mjs`, вставленный в консоль Safari (Web Inspector → Timelines → Rendering Frames).
- Дисплей отдаёт 120 Гц (кадр 8,3 мс), поэтому худший кадр 18 мс — уже пропуск.

| G4 | 4 × `feComposite arithmetic` (`map`, `rg`, `bent` и финальный `in`) | По данным PR Glass-HQ, арифметика в WebKit идёт программно и занимала > 50 % времени фильтра | Сборку каналов делать через `feBlend mode="screen"` (если в одном из слоёв канал равен 0, screen даёт ровно сумму) или `feMerge`, если каналы уже разнесены по прозрачности [проверить в Safari] |

Для шапки — либо один проход плюс цветной сдвиг кромки, либо оставить, если замер в Safari скажет, что это не главное |
| G6 | `update()` на каждый scroll | Чтение трёх rect и запись transform 2–4 копиям. Дёшево, но в Safari каждая запись = пересчёт фильтра | Двигать копию только когда сдвиг > 0,5 px. Когда фото ушло из-под шапки, отписываться (IntersectionObserver на `.hero__photo`) |
| G7 | `brightness()` рисует кусок 2000-пиксельной картинки в canvas | Синхронно и с декодированием. Кэш по полосам 40 px есть, но первый проход на каждом слайде идёт при прокрутке | Посчитать яркость полос заранее в build.py (8–10 чисел на слайд в `data-tone`) |

### Хрупко

| # | Что | Последствие |
|---|---|---|
| G8 | Копии под кнопками ▶ делаются без `loading` | Постеры всех видео грузятся сразу при открытии страницы [замер Chrome: video-company, video-m5 на 70 мс]. Правка: копировать `loading`, а копию заводить при первом пересечении (IntersectionObserver) |
| G9 | `ResizeObserver` следит только за `img`, а не за `host` | Если плашка-подпись поменяет ширину от шрифта или текста, копия под ней съедет. Надо наблюдать и хост |
| G10 | `matchMedia(...)` проверяется один раз при загрузке | Окно сузили — стекло остаётся, расширили — не появляется. Для плагина нужен слушатель `change` |
| G11 | `prefers-reduced-transparency` не поддерживают Safari и Firefox (caniuse) | Главная аудитория (Safari) с включённым «Уменьшить прозрачность» видит стекло. Из веба эту настройку в Safari не узнать. Можно хотя бы учитывать `prefers-contrast: more`, оставить ручной выключатель и не делать стекло фоном для текста, без которого текст не читается |
| G12 | `prefers-reduced-motion` в glass.js не учитывается | Кроссфейд слоёв 900 мс и появление линзы идут и при «Уменьшить движение». В CSS это закрыто только для `.hero__photo > img` |
| G13 | Фиксированные id `glass-bar`, `glass-dot` | Safari кэширует фильтр по id, и смена настроек без перезагрузки не применится. На сайте это пока не важно, в плагине нужен счётчик (как в лаборатории) |
| G14 | Настройки из `localStorage('dioGlass')` подмешиваются на живом сайте | Владелец лаборатории видит сайт не так, как посетители, и может ошибочно решить, что «на сайте сломалось». В плагине лучше только `?glass-debug` |
| G15 | `brightness()` молча возвращает 1 при ошибке canvas | Для чужих картинок (другой домен без CORS) тон всегда «светлый». В плагине нужно явное `crossorigin` или ручной тон |
| G16 | Логика шапки завязана на `.nav__row`, `.hero__photo`, `.hero__panel` и событие `slide` | Это клей сайта, а не плагин |

### Где не заработает

| Браузер | Что будет | Основание |
|---|---|---|
| Chrome / Edge (Mac, Win) | Работает, быстро | замер Chrome |
| Chrome Android | Выключено условием `pointer: coarse`; без него — неизвестно | из кода |
| Safari macOS 27 | Работает, худший кадр 33 мс (замер владелец сайтаа, CONTEXT.md) | CONTEXT.md |
| Safari iOS/iPadOS | Выключено условием `max-width`/`pointer: coarse`. iPad с трекпадом и окном шире 60rem даёт `pointer: fine` → стекло включится, и будет плохо | из кода, [гипотеза] |
| Firefox | `filter:url()` на HTML поддерживается. Но по данным PR Glass-HQ, Gecko отправляет любой фильтр с `feDisplacementMap` на процессор и перерисовывает его при любой перерисовке страницы | [не проверено здесь] |
| Встроенные браузеры (Telegram, VK, Яндекс на iOS) | Это WebKit, ведут себя как Safari iOS | [гипотеза] |

Почему в Chrome стекло выглядит иначе, чем в Safari (гипотезы для проверки в настоящем Safari):
- `color-interpolation-filters` по умолчанию `linearRGB`. Нейтраль карты 0,5 считается в линейном пространстве. Если движок переводит `in2` у `feDisplacementMap` в другое пространство, вся капсула сдвинется на постоянную величину (до ≈ 0,23 × |bend| ≈ 30 px при bend −140). Проверка: снимок решётки под стеклом в обоих браузерах. Если причина в этом, `color-interpolation-filters="sRGB"` надо ставить на отдельные примитивы, а не на `<filter>` (на `<filter>` Safari рисует пусто). Спецификация и старое расхождение браузеров по feDisplacementMap — в списке источников.
- Разное разрешение фильтра: Chrome считает при DPR устройства, Safari может считать при другом масштабе — тогда «мягкость» и ширина кромки разные.

## Что переносить в плагин

Берём почти как есть:
- **`filter(id, opts)`** — чистая функция, строка SVG без DOM. Основа генератора, но с правками G2 (область под размер), G4 (без arithmetic), G13 (id со счётчиком).
- **Схема линза > обрезка > копия** (`lensFor`) и правило «только 2D translate внутри линзы». Это наш собственный, проверенный в Safari опыт, в чужих реализациях его нет.
- **`overImage`**: копия картинки, выставленная по `getBoundingClientRect`, плюс ResizeObserver. Для плагина нужен режим «стекло над одной картинкой», это самый дешёвый честный случай.
- **Кроссфейд слоёв под стеклом** — как идея, но с решением C2.
- **Тон по яркости с гистерезисом 0,42/0,58** — полезная часть, вынести в отдельную опцию; яркость лучше брать заранее.
- **`.is-glass::before`** (тон, блик, кромка, тень) — CSS-слой, одинаковый во всех браузерах.
- **Лаборатория** — как демо и стенд настройки плагина, с добавленным счётчиком кадров.

Не берём:
- селекторы и логику сайта (`.nav__row`, `.hero__*`, событие `slide`, `?glass=liquid`), `window.dioGlass`, `localStorage` на живых страницах;
- `cloneNode(true)` фона (тормоза, рассинхрон, дубли для скринридеров; на это же жалуется issue w3c/svgwg #1142).

Направления, которые аудит подсказывает для плагина (подробно — в других отчётах `research/`):
1. **Стекло над картинкой (шапка над фото, кнопки на видео) можно рисовать в WebGL**: картинка своего домена → текстура, преломление и аберрация в шейдере на видеокарте. Тогда Safari и iPhone не упираются в процессорный путь SVG-фильтров. Пока это гипотеза, нужен замер.
2. **Где остаётся SVG**: область под размер, без arithmetic, карту — через `feImage` там, где он работает (Chromium, Firefox), и вычислять в фильтре только в Safari.
3. **Для Firefox** — проверить `-moz-element()` как живую копию без клона DOM (так делает Glass-HQ/liquid-glass, PR #3).

- kube.io, «Liquid Glass in the Browser: Refraction with CSS and SVG» — карта через `feImage`, `backdrop-filter: url()` только в Chrome, пересборка карты дорогая: https://kube.io/blog/liquid-glass-css-svg/ ; обсуждение на HN (Safari медленнее): https://news.ycombinator.com/item?id=45174297
- Glass-HQ/liquid-glass, PR #3 «perf: cross-browser glass rendering for Gecko and WebKit» — Gecko отправляет feDisplacementMap/feImage на CPU; в WebKit арифметический composite программный; `-moz-element()`; замеры автора на M4 Pro (не независимые): https://github.com/Glass-HQ/liquid-glass/pull/3
- w3c/svgwg issue #1142 — нет совместимого способа преломлять подложку; WebKit bug 245510 (`backdrop-filter: url()` с feDisplacementMap); минусы клонирования DOM: https://github.com/w3c/svgwg/issues/1142
- emribilemir/liquid-glass-research — замеры настоящего стекла macOS; в Chromium общий результат фильтра пересчитывается для каждого читателя, и автор разнёс стекло на два слоя: https://github.com/emribilemir/liquid-glass-research
- Chromium, «Filter Effects» (design doc, старый) — CSS `url()`-фильтры идут по GPU-пути только для уже композитных источников: https://www.chromium.org/developers/design-documents/image-filters/
- caniuse, `prefers-reduced-transparency` — Chromium 118+, в Safari и Firefox нет: https://caniuse.com/wf-prefers-reduced-transparency ; https://developer.chrome.com/blog/css-prefers-reduced-transparency
- Расхождение браузеров по feDisplacementMap (2017): https://lists.w3.org/Archives/Public/public-fxtf-archive/2017Dec/0050.html
- MDN, feDisplacementMap: https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/feDisplacementMap
- Mozilla bug 925025 (CSS blur в Firefox: программный путь до WebRender): https://bugzilla.mozilla.org/show_bug.cgi?id=925025
