# Плагин жидкого стекла: GPU-путь (WebGL2-шейдер по Снеллиусу)

Черновик проекта, 30.10.2026. Кода пока нет, это архитектура и план проверки.
Опирается на `../CONTEXT.md` и `../research/*.md` (apple, audit, browsers, fresh, graphics,
implementations, performance). Живой сайт `<сайт>/` не трогал.

Метки:
- **[S27]** — проверено владелец сайтаом в настоящем Safari 27 (из CONTEXT.md);
- **[ист.]** — по источникам, ссылка рядом; в настоящем Safari нами не проверено;
- **[оценка]** — мой расчёт или вывод, ничем не измерено;
- **[проверить в Safari]** — без замера в настоящем Safari или на iPhone не принимать. Playwright-WebKit
  доказательством не считается [S27].

## 0. Коротко

1. **Стекло рисует WebGL2-шейдер в `<canvas>` внутри элемента-стекла.** Картинка за стеклом —
   **текстура из того же `<img>`/`<video>`/`<canvas>`**, что лежит под ним на странице. Захвата DOM нет.
   Под шапкой сайт-пример всегда одно фото-слайд, так что этого хватает.
2. **Оптика честная:** форма — SDF скруглённого прямоугольника с аналитическим градиентом, высота
   кромки — профиль «выпуклый сквиркл», нормаль из производной высоты, `refract()` с n = 1,5,
   сдвиг выборки = путь луча в стекле и в зазоре до фона. Аберрация — свой показатель преломления на
   каждую из 3–5 спектральных выборок. Блик — Френель (Шлик) плюс направленный блик по той же нормали.
   Матовость — мип-уровни текстуры. Тень — обычный CSS `box-shadow`.
3. **Цена:** один квадрат на GPU, ~0,26 Мп на Mac и ~0,18 Мп на iPhone. По чужому замеру сопоставимый
   шейдер стоит 0,13–0,22 мс GPU на M2 Pro ([m2-md](https://github.com/m2-md/liquid-glass-refraction-shader/blob/main/README.md)).
   Сейчас SVG-фильтр в Safari даёт худший кадр 33 мс [S27]. Ожидаю выигрыш на один-два порядка [оценка, проверить в Safari].
4. **Главный риск не скорость, а отставание от прокрутки.** Шапка липкая, фото уезжает под ней, а
   canvas перерисовывается из JS. Картинка в линзе может отставать от фото вокруг на кадр. Для
   стекла, которое едет вместе со своей картинкой (кнопки на видео, подпись и «пауза» на фото),
   этой проблемы нет совсем: сдвиг между ними постоянный. Первым прототипом мерим именно отставание.
5. **SVG и CSS — только запасной путь:** нет WebGL2, программный WebGL, потеря контекста, провал
   замера кадров → матовое `backdrop-filter` с CSS-кромкой; «Уменьшить прозрачность» / высокий
   контраст → сплошная плашка. SVG-фильтр в плагин по умолчанию не входит (только как модуль для
   Chromium над живым DOM).
6. **Библиотек нет.** Свой код ~600–800 строк, ~10–14 КБ после минификации, ~5 КБ gzip [оценка].
   three.js ради одного квадрата ~150 КБ gzip ([graphics.md](../research/graphics.md)). WebGPU и WASM не нужны (раздел 9).

## 1. Что делает плагин и чего не делает

Делает: стекло над **картинкой, видео или canvas**, если известно, какая картинка под ним и где она
лежит. Это шапка над фото первого экрана, кнопки ▶ на постерах видео, подпись и кнопка «пауза» на
фото, в будущем любые плашки на фото товаров.

Не делает: стекло над **произвольным DOM** (текст, карточки). WebGL не видит пиксели страницы. Снимок
DOM (html-to-image, foreignObject) стоит 100–500 мс и в WebKit ненадёжен
([ybouane/liquidglass](https://github.com/ybouane/liquidglass), [WebKit 180301](https://bugs.webkit.org/show_bug.cgi?id=180301)).
HTML-in-Canvas есть только в Chromium по origin trial ([Chrome](https://developer.chrome.com/blog/html-in-canvas-origin-trial)).
Над DOM у нас матовое стекло. По логике Apple это и есть вариант Regular ([apple.md](../research/apple.md), раздел 6).

## 2. API

### 2.1 Подключение

Один ES-модуль без зависимостей и один CSS-файл, лежат рядом с сайтом:
`assets/liquid-glass.js` и `assets/liquid-glass.css`. Внешних CDN нет.

```html
<link rel="stylesheet" href="/assets/liquid-glass.css">
<script type="module" src="/assets/сайт-пример-glass.js"></script>  <!-- клей сайта, см. раздел 8 -->
```

```js
import { glass } from '/assets/liquid-glass.js';

const g = glass(document.querySelector('.nav__row'), {
  source: () => document.querySelector('.hero__photo > img.is-on'), // что за стеклом
  frame:  document.querySelector('.hero__photo'),                   // где эта картинка лежит (бокс object-fit)
  pinned: true,              // стекло стоит на экране (sticky/fixed), картинка прокручивается
  preset: 'bar',             // 'bar' | 'pill' | 'dot' | объект с параметрами ниже
});

g.set({ thickness: 16 });     // поменять параметры без пересборки (только uniform'ы)
g.source(nextImg);            // сменить картинку; кроссфейд берётся из CSS-перехода самой img
g.state;                      // 'gpu' | 'frost' | 'solid' | 'off' — что сейчас видит пользователь
g.on('state', s => …);        // смена пути (потеря контекста, провал замера)
g.destroy();
```

Декларативный вариант для простых случаев (кнопки на постерах): `data-glass` на хосте и
`data-glass-source="<селектор>"`. Плагин ищет такие элементы сам, при первом пересечении с экраном
(IntersectionObserver), а не при загрузке страницы.

Что плагин делает с хостом:
- вставляет первым ребёнком `<canvas class="lg-canvas" aria-hidden="true">` на всю площадь хоста,
  `pointer-events: none`. Ссылки и текст остаются DOM поверх canvas;
- ставит хосту класс состояния `lg-gpu` / `lg-frost` / `lg-solid`. Фон, `backdrop-filter`, CSS-кромка
  и тень переключаются этими классами в `liquid-glass.css`;
- радиус берёт из `getComputedStyle(host).borderRadius` (у капсулы это половина высоты).

### 2.2 Параметры

Все в CSS-пикселях и долях. Все, кроме `source/frame/pinned`, — uniform'ы шейдера: менять можно
хоть каждый кадр, пересборки нет (в отличие от SVG, где Safari кэширует фильтр по id [S27]).

| Параметр | По умолчанию (bar) | Смысл |
|---|---|---|
| `bevel` | 14 px | ширина кромки, где поверхность изгибается. Середина плоская и картинку не сдвигает |
| `thickness` | 12 px | высота стекла над плоскостью в середине |
| `gap` | 8 px | зазор между стеклом и фоном: стекло «парит», как у Apple. От него зависит, насколько сильно гнётся картинка у самого края |
| `profile` | `'squircle'` | профиль кромки: `'squircle'` y = ⁴√(1−(1−x)⁴), `'circle'` y = √(1−(1−x)²), `'lip'` (как у переключателя Apple) ([kube.io](https://kube.io/blog/liquid-glass-css-svg/)) |
| `ior` | 1,5 | показатель преломления стекла |
| `dispersion` | 0,04 | разброс n между красным и синим (у настоящего стекла ~0,01, для заметности усилен) |
| `samples` | 5 (Mac), 3 (телефон) | число спектральных выборок аберрации: 1 = без аберрации |
| `frost` | 0,6 | матовость: мип-уровень сверх «родного», 0 = чистое стекло |
| `saturate` | 1,5 | насыщение картинки под стеклом |
| `tint`, `tintColor` | 0,26, белый | тонировка (наш «тон 26 %») |
| `lightAngle` | −60° | откуда свет (сверху-слева, как у kube.io и Apple) |
| `specular` | 0,5 | сила направленного блика |
| `rim` | 0,4 | сила френелевской светлой кромки (наша «кромка 40 %») |
| `shadow` | 0,7 | сила CSS-тени (наша «тень 70 %»), через `--lg-shadow` |
| `dpr` | `min(devicePixelRatio, 2)` | разрешение canvas |
| `quality` | `'auto'` | `'auto'` снижает `samples`, затем `dpr`, затем уходит в `frost` по замеру кадров (раздел 6.3) |
| `predict` | `false` | экстраполировать прокрутку на кадр вперёд (раздел 7.1, гипотеза) |

Старые настройки из лаборатории (rim 4.5 / bend −140) в новые однозначно не переводятся: там карта из
Собеля по размытой маске, здесь геометрия. Пресеты придётся подобрать заново в лаборатории (раздел 10).
Ориентир: `bevel ≈ 3·rim`, знак `bend < 0` (край тянет картинку внутрь) соответствует выпуклому профилю.
Выпуклая поверхность «держит лучи внутри»: у кромки видна картинка чуть глубже от края
([kube.io](https://kube.io/blog/liquid-glass-css-svg/)).

### 2.3 Пресеты

- `bar` — шапка-капсула (~1100×60): bevel 14, thickness 12, gap 8, samples 5.
- `pill` — подписи на фото: bevel 10, thickness 8, gap 4, samples 3.
- `dot` — круглые кнопки 44–64 px: bevel 16, thickness 14, gap 6, samples 3, `profile: 'circle'`.

Пресеты выбираются по размеру, а не по имени элемента (замечание L5 из [audit.md](../research/audit.md)).

## 3. Откуда берётся картинка за стеклом

### 3.1 Источники

| `source` | Как попадает в текстуру | Когда перезаливается |
|---|---|---|
| `HTMLImageElement` | `await img.decode()` → `createImageBitmap(img)` → `texImage2D` + `generateMipmap` | только при смене `src` / слайда |
| `HTMLVideoElement` | `texImage2D(video)` в `requestVideoFrameCallback` | только на новом кадре видео, не на каждом rAF ([web.dev](https://web.dev/articles/requestvideoframecallback-rvfc)) |
| `HTMLCanvasElement` / `OffscreenCanvas` | `texImage2D(canvas)` | по `g.invalidate()` от владельца canvas |
| функция `() => element` | вызывается при `g.source()` и на событиях хоста | — |

Правила:
- **Картинка того же домена.** У сайт-пример всё своё, CORS не нужен. Для чужих картинок нужен
  `crossorigin`, иначе WebGL откажет в загрузке текстуры.
- **Брать уже загруженный `currentSrc`** (на телефоне это `-1000.webp`). Текстура ~1000×562 весит
  ~2,2 МБ, с мипами ~3 МБ [оценка]. Свою «уменьшенную копию для стекла» в build.py можно добавить
  позже, если замер на iPhone покажет нехватку памяти. Для 1920-пиксельного оригинала на Mac можно
  ограничить текстуру `maxTexture: 1280` и уменьшать через `createImageBitmap(img, {resizeWidth})`
  [ист.: поддержка опций `resize*` в Safari — проверить в Safari].
- **Декодирование не в кадре прокрутки.** Следующий слайд готовить сразу после смены предыдущего
  (через `requestIdleCallback`, а где его нет — `setTimeout`): `decode()` → `createImageBitmap` →
  заливка во вторую текстуру. К моменту смены слайда текстура уже лежит на GPU. Это заодно
  лечит рывок S1 из аудита.
- **Цвет.** Canvas и `<img>` по умолчанию оба sRGB и оба приводятся к цветам дисплея браузером.
  Центр линзы должен совпадать с фото вокруг до пикселя. Настройки `UNPACK_COLORSPACE_CONVERSION`
  оставляем по умолчанию. Совпадение проверяем решёткой и цветной заливкой [проверить в Safari].

### 3.2 Где картинка лежит относительно стекла (без чтения раскладки в кадре)

Нужно сопоставить точку стекла (CSS-px, от левого верхнего угла хоста) и UV текстуры.

Один раз (при старте, по `ResizeObserver` хоста и `frame`, по `scrollend`) читаем:
- `frameDoc` — бокс картинки в координатах документа (`getBoundingClientRect` + `scrollX/Y`);
- `hostRect` — бокс стекла: для `pinned` в координатах окна, иначе в координатах документа;
- `object-fit` и `object-position` картинки → масштаб и сдвиг: для `cover`
  `s = max(W/w, H/h)`, `dw = w·s`, `dh = h·s`, `ox = (W − dw)·px`, `oy = (H − dh)·py`.

В кадре JS делает одно: `uScroll = scrollY` (для `pinned`). Шейдер:
`rel = hostPos + p − (frameDoc − scroll)` → `uv = (rel − o) / d`. Это одна матрица 3×3 `uToUV` и
один uniform. `getBoundingClientRect` на каждой прокрутке больше не нужен (у нас сейчас он есть,
G6 в аудите). По `scrollend` (Safari 26.2+, [InfoQ](https://www.infoq.com/news/2026/04/safari-scrollend-support))
перечитываем рамки на случай дрейфа (адресная строка iOS, `svh`).

Для стекла, которое едет вместе с картинкой (`pinned: false`), `uToUV` постоянна, и при
прокрутке canvas не перерисовывается вообще. Его двигает композитор вместе со страницей, отставать нечему.

### 3.3 Кроссфейд слайдов

На сайте `<img>` слайдов меняются CSS-переходом `opacity 900ms`. В шейдере две текстуры и
`mix(A, B, uMix)`. `uMix` в каждом кадре перехода берётся из **той же самой** анимации:
`img.getAnimations()[0]?.effect.getComputedTiming().progress` с той же кривой
(`--ease-in-out: cubic-bezier(0.65, 0, 0.35, 1)`) или просто `getComputedStyle(img).opacity`.
Так линза и фото вокруг меняются синхронно. rAF крутится только 900 мс перехода. При «Уменьшить
движение» CSS уже ставит `transition: none`, и шейдер переключится мгновенно сам.

Внутри линзы при этом нет DOM-копий, а значит нет и опасности C2 из аудита («слой копии уходит в
композитный слой, преломление пропадает»).

## 4. Как считается картинка (шейдер)

### 4.1 Схема кадра

```
p (CSS-px от центра стекла)
 └─ SDF скругл. прямоугольника + аналит. градиент  →  d (расстояние до края), ĝ (наружу)
     └─ x = clamp(−d / bevel, 0, 1)  →  высота z = thickness · h(x),  наклон z' = thickness · h'(x) / bevel
         └─ нормаль N = normalize(z' · ĝ, 1)
             └─ для каждой из K спектральных выборок λ:
                  n(λ) = ior + dispersion · (λ − ½)
                  R = refract((0,0,−1), N, 1/n(λ))
                  смещение = R.xy · (z + gap) / −R.z
                  цвет += вес(λ) · textureLod(tex, uv(p + смещение), lod)
         └─ насыщение, тон
         └─ Френель (Шлик) по cosθ = N.z  →  светлая кромка
         └─ направленный блик по N и свету  →  яркая дуга сверху-слева, слабее снизу-справа
 └─ альфа = покрытие пикселя формой (сглаживание края), выход с премультипликацией
```

### 4.2 Форма: SDF и градиент

Расстояние со знаком до скруглённого прямоугольника и его градиент **аналитически**, по Inigo Quilez
([distgradfunctions2d](https://iquilezles.org/articles/distgradfunctions2d),
[distfunctions2d](https://iquilezles.org/articles/distfunctions2d); код на сайте автора под MIT,
по его же словам). Градиент через `dFdx/dFdy` не годится: он считается блоками 2×2 и даёт
ступеньки на кромке, а кромка и есть главное.

Для капсулы радиус = половина высоты, и SDF точный. Сквиркл-углы Apple (непрерывная кривизна) нужны
только для кнопок с небольшим радиусом. Там «расстояние» по норме L4 (`pow(q.x⁴+q.y⁴, ¼)`):
оно не евклидово, поэтому градиент нормируем. Глазом разницу на капсуле не увидеть [оценка].

### 4.3 Профиль кромки и Снеллиус

- `h(x)` — выпуклый сквиркл `(1 − (1−x)⁴)^¼`, производная аналитически:
  `h'(x) = (1−x)³ · (1 − (1−x)⁴)^(−¾)`. У самого края (x→0) наклон бесконечный. Берём
  `x ≥ 0,002` и ограничиваем смещение `maxShift` (≈ bevel), иначе у края шум и выход за текстуру.
- Луч от зрителя `I = (0, 0, −1)` (страница плоская, смотрим перпендикулярно).
  `R = refract(I, N, 1/ior)` — это и есть закон Снеллиуса n₁·sinθ₁ = n₂·sinθ₂ в векторной
  форме (GLSL `refract`). Полного внутреннего отражения на входе в стекло (воздух → стекло) не бывает.
- Смещение точки выборки: луч идёт в стекле от поверхности (высота z) до дна и дальше через зазор
  `gap` до картинки. Дно плоское и параллельно фону, поэтому на выходе из стекла направление
  возвращается почти к исходному. Для простоты (и как у Unreal «Pixel Normal Offset», где плоская
  часть не сдвигает картинку, [Epic](https://dev.epicgames.com/documentation/unreal-engine/refraction-using-pixel-normal-offset-in-unreal-engine))
  считаем сдвиг одним отрезком: `off = R.xy · (z + gap) / −R.z`.
  Вариант «честнее» с двумя преломлениями (вход по N, выход через плоское дно в зазор)
  стоит ещё один `refract` на выборку. Включается флагом `exitRefraction` и сравнивается в лаборатории.
- В плоской середине N = (0,0,1) → R = I → смещение 0: центр не искажён. По Apple это главное
  условие узнаваемости ([apple.md](../research/apple.md), раздел 1).

### 4.4 Аберрация (дисперсия)

Свой n на каждую выборку. При K = 3 это R/G/B, у каждого свой `refract`. При K = 5 веса по
«спектру» (красный → жёлтый → зелёный → голубой → синий) нормированы так, что сумма весов по каждому
каналу равна 1. Тогда белое остаётся белым, а на кромке получается мягкая радуга, а не три
резких контура. Цена — около 0,012 мс GPU на выборку на M2 Pro ([m2-md](https://github.com/m2-md/liquid-glass-refraction-shader/blob/main/README.md)).
Аберрация физически появляется только там, где есть наклон, то есть только у кромки: отдельная
маска не нужна. Для оптики сайт-пример это, по-моему, самая «их» деталь, её стоит оставить даже на телефоне (K = 3).

### 4.5 Матовость, насыщение, тон

- Матовость: `textureLod(tex, uv, lodBase + frost)`, где `lodBase = log2(текселей на пиксель экрана)`.
  Мипы трилинейные и дают блочность на больших `frost`. При `frost > 1,5` берём 4 выборки по
  повёрнутому кресту на том же lod ([Grassi](https://charlesgrassi.dev/blog/apple-liquid-glass/)).
  Apple размывает мало ([apple.md](../research/apple.md), раздел 0), так что обычно хватает одной выборки.
- Насыщение: `mix(vec3(luma), col, saturate)`. Тон: `mix(col, tintColor, tint)`.
- Тон «под фон» дешевле всего считать прямо в шейдере: средний цвет под стеклом — это
  `textureLod(tex, uvЦентра, 7.0)`, без чтения пикселей на CPU. А вот цвет **текста** шапки
  (`is-dark`) — это DOM, его считаем заранее в build.py (`data-tone`, как советует аудит, S3/G7).

### 4.6 Блик и светлая кромка

- Френель по Шлику: `F = 0,04 + 0,96·(1 − N.z)⁵`; `col = mix(col, white, F·rim)`. Кромка светлеет
  сама там, где поверхность круто наклонена. Это физическая замена нашей «кромке 40 %».
- Направленный блик: `L` из `lightAngle` (−60°) с наклоном к экрану, `spec·pow(max(dot(N, H), 0), 40)`,
  `H = normalize(L + V)`. Плюс вдвое слабее с противоположной стороны (отражение от дальней стенки).
  Получается яркая дуга сверху-слева и тусклая снизу-справа, как у Apple ([kube.io](https://kube.io/blog/liquid-glass-css-svg/), [Grassi](https://charlesgrassi.dev/blog/apple-liquid-glass/)).
- Движение блика (курсор или гироскоп) — это просто uniform `lightAngle`. При «Уменьшить движение» его не трогаем.
- Сглаживание края: `alpha = clamp(0,5 − d·dpr, 0, 1)`, выход с премультипликацией
  (`premultipliedAlpha: true`). Снаружи формы canvas прозрачный, поэтому скругление canvas через CSS
  не нужно. Это обходит и баг Firefox, где WebGL-canvas не обрезается `border-radius`
  ([implementations.md](../research/implementations.md), п. 5).

### 4.7 Тень

Тень — снаружи формы, а canvas размером с хост, поэтому её рисует CSS:
`box-shadow: 0 8px 24px rgb(0 0 0 / calc(.2*var(--lg-shadow))), 0 1px 3px …` на хосте. Это стоит ~0
и одинаково везде ([apple.md](../research/apple.md), раздел 5). Внутренняя «толщина» (лёгкое затемнение
у нижней кромки) — в шейдере, по `N.y`, одной строкой.

### 4.8 Набросок фрагментного шейдера (GLSL ES 3.0)

```glsl
#version 300 es
precision highp float;
uniform sampler2D uA, uB;  uniform float uMix;
uniform vec2  uHalf;       // половина размера стекла, CSS px
uniform float uR, uDpr;    // радиус скругления, плотность пикселей
uniform mat3  uToUV;       // CSS px стекла (от левого верхнего угла) → UV картинки; прокрутка уже внутри
uniform float uBevel, uThick, uGap, uIor, uDisp, uMaxShift, uLod, uSat, uTint, uRim, uSpec;
uniform vec3  uTintColor, uL;   // uL — направление на свет (нормированное)
in vec2 vP;                // CSS px от центра стекла, y вниз
out vec4 o;

vec3 sdgRoundBox(vec2 p, vec2 b, float r) {      // по I. Quilez (MIT): x = расстояние, yz = градиент
  vec2 w = abs(p) - (b - r);
  vec2 s = vec2(p.x < 0. ? -1. : 1., p.y < 0. ? -1. : 1.);
  float g = max(w.x, w.y); vec2 q = max(w, 0.); float l = length(q);
  vec2 n = s * (g > 0. ? q / l : (w.x > w.y ? vec2(1, 0) : vec2(0, 1)));
  return vec3((g > 0. ? l : g) - r, n);
}
vec3 tap(vec2 p) {                                // цвет картинки в точке p (CSS px от центра)
  vec2 uv = (uToUV * vec3(p + uHalf, 1.)).xy;
  return mix(textureLod(uA, uv, uLod).rgb, textureLod(uB, uv, uLod).rgb, uMix);
}
const int K = 5;                                  // спектральные выборки (3 на телефоне)
const vec3 W[5] = vec3[](vec3(.55,0,0), vec3(.45,.25,0), vec3(0,.5,0), vec3(0,.25,.45), vec3(0,0,.55));

void main() {
  vec3 sg = sdgRoundBox(vP, uHalf, uR);
  float d = sg.x; vec2 gOut = sg.yz;
  float a = clamp(.5 - d * uDpr, 0., 1.);  if (a <= 0.) discard;

  float x  = clamp(-d / uBevel, .002, 1.);
  float u  = 1. - x, u4 = u*u*u*u;
  float h  = pow(1. - u4, .25);                   // выпуклый сквиркл
  float dh = u*u*u * pow(1. - u4, -.75);          // h'(x)
  float z  = uThick * h;
  vec3  N  = normalize(vec3(gOut * uThick * dh / uBevel, 1.));

  vec3 col = vec3(0);
  for (int i = 0; i < K; i++) {
    float t = float(i) / float(K - 1) - .5;       // −½ (красный) … +½ (синий)
    vec3  R = refract(vec3(0, 0, -1), N, 1. / (uIor + uDisp * t));
    vec2  off = R.xy * (z + uGap) / -R.z;
    off *= min(1., uMaxShift / max(length(off), 1e-4));
    col += W[i] * tap(vP + off);
  }
  float lum = dot(col, vec3(.2126, .7152, .0722));
  col = mix(vec3(lum), col, uSat);
  col = mix(col, uTintColor, uTint);
  float F = .04 + .96 * pow(1. - N.z, 5.);        // Шлик
  col = mix(col, vec3(1), F * uRim);
  vec3 H = normalize(uL + vec3(0, 0, 1));
  col += uSpec * (pow(max(dot(N, H), 0.), 40.) + .5 * pow(max(dot(N, H * vec3(-1,-1,1)), 0.), 40.));
  o = vec4(col * a, a);                           // премультипликация
}
```

Вершинный шейдер — один треугольник на весь canvas, `vP = clip.xy · uHalf · (1, −1)`.
Число выборок `K` — константа при компиляции: держим две программы (K = 5 и K = 3) и K = 1 для
режима «экономия». Переключение между ними без перекомпиляции в кадре.

## 5. Рисование и жизненный цикл

- **Контекст:** `canvas.getContext('webgl2', { alpha: true, premultipliedAlpha: true, antialias: false,
  depth: false, stencil: false, preserveDrawingBuffer: false, powerPreference: 'low-power',
  failIfMajorPerformanceCaveat: true })`. Последний флаг отсекает программный WebGL (SwiftShader в
  Chrome при заблокированном GPU). Там стекло стоило бы дороже SVG, и мы уходим в `frost`.
- **Один контекст на стекло**, предел 8 на страницу (браузеры держат ~16 контекстов и молча
  теряют старые, [Chrome](https://developer.chrome.com/docs/web-platform/webgpu/from-webgl-to-webgpu)).
  У сайт-пример стёкол 4–6: шапка, пауза, подпись, 2–3 кнопки видео. Общий холст поверх всей страницы
  не берём: на iPhone это слой ~12 МБ, и он прокручивался бы из JS
  ([performance.md](../research/performance.md), 5.6). Копировать из одного WebGL-canvas в другие
  через `drawImage` медленно и в Firefox, и в Safari ([Mozilla 1163426](https://bugzilla.mozilla.org/show_bug.cgi?id=1163426)).
  Если стёкол станет больше 8, попробовать один `OffscreenCanvas` + `transferToImageBitmap` в
  `bitmaprenderer`-холсты [ист., проверить в Safari].
- **Рисуем только по событию.** Вечного rAF нет. `invalidate()` ставит один rAF. Поводы для кадра:
  прокрутка (только у `pinned`, и только пока картинка под стеклом), кроссфейд, новый кадр видео,
  ресайз, `g.set()`.
- **Когда не рисуем вообще:** IntersectionObserver на `frame` с `rootMargin` по высоте шапки.
  Фото ушло из-под шапки → стекло переходит в `frost` (CSS-переход opacity 200 мс), слушатель
  прокрутки снимается. `document.hidden` → всё стоп.
- **Ленивый старт:** контекст, шейдер и текстуры создаются при первом пересечении, а не на загрузке
  (так лечил вылеты Safari Ash Kyd, [ashk.au](https://ashk.au/2024/02/07/dev-log-debugging-safari-an-ogre-with-layers/)).
- **Потеря контекста:** `webglcontextlost` → `preventDefault()`, сразу `frost`. По `webglcontextrestored` —
  пересоздать текстуры и вернуться в `gpu`. iOS теряет контексты фоновых вкладок [ист., проверить на iPhone].
- **Ресайз:** `ResizeObserver` на хост **и** на `frame` (G9 в аудите). Canvas: `width = round(w·dpr)`.
  После `destroy()` — `canvas.width = canvas.height = 0`: iOS не сразу освобождает память холстов
  ([pqina](https://pqina.nl/blog/total-canvas-memory-use-exceeds-the-maximum-limit/)).
- **`matchMedia(...).addEventListener('change')`** для всех медиазапросов (G10 в аудите).
- **Печать:** `@media print { .lg-canvas { display: none } }` и сплошная плашка.

## 6. Запасные пути и выбор пути

### 6.1 Лестница

```
gpu  (WebGL2-шейдер)      ← есть WebGL2, не программный, замер кадров в норме, нет «уменьшить прозрачность»
 ↓ нет WebGL2 / потеря контекста / failIfMajorPerformanceCaveat / провал замера
frost (CSS)               ← backdrop-filter: blur(20px) saturate(1.8) + CSS-кромка (::before, 3 inset-тени) + box-shadow
 ↓ нет backdrop-filter / Firefox Android (тормозит прокрутка, bug 1732817) / prefers-contrast: more
solid                     ← непрозрачная плашка с рамкой 1 px
off                       ← forced-colors: active — системные цвета, никакого стекла
```

SVG-фильтр (`backdrop-filter: url()` с готовой картой) — отдельный необязательный модуль
`liquid-glass-svg.js` для стекла **над живым DOM**, только в Chromium. Определять его по движку, а не
по `@supports`: Firefox и Safari отвечают «да» и ничего не рисуют
([browsers.md](../research/browsers.md), раздел 2). Для шапки над фото он больше не нужен.

WebGL1 сознательно не поддерживаем: WebGL2 есть в Safari с iOS 15 / macOS 12 и во всех живых
браузерах ([testmuai](https://www.testmuai.com/learning-hub/webgl-2-browser-compatibility/)), а
поддержка WebGL1 удвоила бы код шейдера (`textureLod` через расширение, нет константных массивов).

### 6.2 Доступность

- `prefers-reduced-transparency: reduce` → `solid`. **В Safari и Firefox этот запрос не работает**,
  WebKit bug 175497 открыт с 2017 года и упирается в приватность
  ([web-features](https://web-platform-dx.github.io/web-features-explorer/features/prefers-reduced-transparency),
  [WebKit 175497](https://bugs.webkit.org/show_bug.cgi?id=175497)). Из веба настройку iPhone «Уменьшить
  прозрачность» не узнать. Что делаем: `prefers-contrast: more` (в Safari есть давно [проверить в Safari]) → `solid`;
  кнопка-переключатель «без стекла» в подвале с запоминанием в `localStorage`. Стекло нигде не
  должно быть единственным фоном под текстом без плашки тона.
- `prefers-reduced-motion: reduce` → блик не двигается, нет анимации появления линзы, кроссфейд
  мгновенный (уже так в CSS). Само преломление при прокрутке — не анимация, а следствие прокрутки: его оставляем.
- `forced-colors: active` → `off`.

### 6.3 Замер на месте (`quality: 'auto'`)

Узнать мощность iPhone из веба нельзя: в Safari нет `navigator.deviceMemory`, GPU-таймеров
(`EXT_disjoint_timer_query`) тоже нет [ист.]. Поэтому меряем сами: первые 2 секунды прокрутки в `gpu`
считаем интервалы rAF и время нашего JS в кадре. Если p95 > 1,25 периода экрана, снижаем ступенями
`samples 5→3→1`, потом `dpr 2→1,5`, потом уходим в `frost` до конца сессии (`sessionStorage`).
Безопасный старт на слабых устройствах — с K = 3 и dpr 1,5. Этот же зонд пишет числа в
`?glass-debug` для замеров (методика — [performance.md](../research/performance.md), раздел 6).
В режиме энергосбережения iOS Safari может ограничивать rAF 30 Гц
([lenis blog](https://www.edoardolunardi.dev/blog/building-smooth-scroll-in-2025-with-lenis)) [проверить на iPhone].
Порог считаем от фактической частоты, иначе на 30 Гц плагин зря уйдёт в `frost`.

## 7. Главный риск: прокрутка

### 7.1 Что происходит

Шапка липкая. Её держит композитор, а фото уезжает под ней тоже на композиторе. Canvas с линзой
мы перерисовываем из JS по `scrollY`. Прокрутка в Safari, Chrome и Firefox асинхронная: JS узнаёт
положение с опозданием, и картинка в линзе может отставать от фото вокруг на кадр, под нагрузкой на
2–3 ([fresh.md](../research/fresh.md) 1.3; [w3c/svgwg#1142](https://github.com/w3c/svgwg/issues/1142);
о том же в Firefox — [Mozilla 949409](https://bugzilla.mozilla.org/show_bug.cgi?id=949409) и обсуждение
в [public-houdini](https://lists.w3.org/Archives/Public/public-houdini/2016Jun/0001.html)).
При 2000 px/с и 60 Гц это до ~33 px. У нынешнего SVG то же самое, только кадр ещё и дорогой.

Важная разница между стёклами:
- **стекло едет вместе со своей картинкой** (пауза и подпись на фото, кнопки на постерах) — сдвиг
  между ними не меняется, canvas при прокрутке не перерисовывается, **отставания нет**;
- **стекло стоит, картинка едет** (шапка над героем) — отставание возможно.

### 7.2 Что с ним делать (по порядку проверки)

1. **Замерить, видно ли его вообще.** Под стеклом изгиб, аберрация и лёгкое размытие. Смещение на кадр
   в середине линзы видно, у кромки почти нет. Запись экрана 120/240 fps и полосатая линейка в
   прототипе (раздел 10). Если на глаз в Safari Mac и на iPhone не видно, ничего не делаем.
2. **Читать `scrollY` в rAF, не в `scroll`.** Слушатель `scroll` (passive) только ставит rAF. Ни
   одного чтения раскладки в кадре (раздел 3.2). Тогда кадр укладывается в доли миллисекунды и
   хотя бы не теряется.
3. **Экстраполяция (`predict: true`)** [гипотеза]: `scrollY + v·Δt`, где v — скорость по двум
   последним кадрам, Δt — период экрана. При ровной прокрутке пальцем или трекпадом это убирает
   кадр отставания. На резкой остановке будет «перелёт» на кадр, его гасит `scrollend`. Включать
   только если п. 1 покажет, что отставание видно.
4. **Матовое на ходу** [ист.: идея из performance.md 5.4]: при скорости > ~1500 px/с плавно (150 мс)
   включаем `frost`, по `scrollend` возвращаем `gpu`. При быстрой прокрутке преломление всё равно не
   разглядеть. Это запасной выход, если 1–3 не помогли.
5. **Крайний вариант:** рисовать в одном canvas и фото героя, и линзу. Тогда они совпадают всегда, но
   отставать начинает уже само фото относительно текста под ним. Скорее всего хуже, держим как эксперимент.

Smooth-scroll-библиотеки (Lenis и т. п., как `syncWith` у [liquidGL](https://github.com/naughtyduk/liquidGL))
не берём: они ломают нативную прокрутку на iPhone и `position: sticky`
([lenis blog](https://www.edoardolunardi.dev/blog/building-smooth-scroll-in-2025-with-lenis)).

- ниже первого экрана шапка остаётся матовой (Regular по Apple) — как сейчас;
- грабли Safari 26: панели браузера тонируются по фону и `backdrop-filter` липких элементов у края
  ([1ar.io](https://1ar.io/updates/safari-26-liquid-glass-web/)). Сам `.nav` прозрачный, стекло и
  canvas — на дочернем слое. Проверить на iPhone [проверить в Safari].

## 9. Почему WebGL2, а не WebGPU, SVG или WASM

| Путь | За | Против | Решение |
|---|---|---|---|
| **WebGL2** | есть везде с 2021 (iOS 15), синхронный старт, ~5 КБ кода, одинаковая картинка во всех движках | нет compute-шейдеров (не нужны) | **основа** |
| WebGPU | есть в Safari 26+, Chrome, Firefox Win/Mac ([gpuweb wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)); `importExternalTexture` для видео без копии | асинхронный старт (`requestAdapter`), нет в Firefox Linux/Android и на iOS < 26; для одного квадрата выигрыша нет (упираемся в заливку пикселей, а не в API); в Safari есть баги с внешними текстурами ([webgpufundamentals](https://webgpufundamentals.org/webgpu/lessons/webgpu-textures-external-video.html)) | позже, вторым бэкендом, если понадобится живое видео или сильное размытие |
| SVG `filter: url()` | работает в Safari [S27] | в Safari на CPU: в WebKit ускоренные фильтры выключены (`AcceleratedFiltersEnabled: false`, [исходники](https://github.com/WebKit/WebKit/blob/main/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml)); худший кадр 33 мс [S27]; разный вид в Chrome и Safari | только запасной модуль для Chromium над DOM |
| WASM | — | та же попиксельная работа на CPU, что у SVG | не нужен |
| HTML-in-Canvas | преломляет живой DOM | только Chromium по токену, API меняется | эксперимент в лаборатории |

Шейдер пишем так, чтобы его было легко перевести на WGSL. Ядро — это чистые функции SDF, профиля и
выборки, без зависимостей от WebGL.

## 12. Риски

| # | Риск | Вероятность / вред | Что делаем |
|---|---|---|---|
| R1 | Картинка в линзе шапки отстаёт от фото на кадр при прокрутке | высокая / средний | раздел 7: замер → экстраполяция → матовое на ходу |
| R2 | Центр линзы не совпадает с фото по цвету или резкости (цветовое пространство, фильтрация текстуры против ресэмплинга `<img>`) | средняя / высокий: «стекло» станет видно как наклейку | решётка и цветные поля в прототипе; подобрать `lodBias`; при расхождении цвета — `drawingBufferColorSpace` и `unpackColorSpace` [проверить в Safari] |
| R3 | Рывок при заливке текстуры на смене слайда (texImage2D синхронный) | средняя / средний | заливка заранее, в простое, после `decode()`/`createImageBitmap` (3.1) |
| R4 | Память и потеря контекста на iPhone (фоновые вкладки, лимит холстов ~224–384 МБ) | средняя / низкий (есть откат) | маленькие текстуры, ≤ 8 контекстов, обработка lost/restored, `width = 0` при уничтожении |
| R5 | Программный WebGL или слабый GPU — стекло дороже SVG | низкая / средний | `failIfMajorPerformanceCaveat`, `quality: 'auto'` |
| R6 | Safari не даёт узнать «Уменьшить прозрачность» | точно / средний (доступность) | `prefers-contrast`, выключатель на сайте, плашка тона под текстом всегда |
| R7 | Тонировка панелей Safari 26 от липкой шапки | средняя / низкий | слои по [1ar.io](https://1ar.io/updates/safari-26-liquid-glass-web/), проверить на iPhone |
| R8 | Новые параметры не дают «того самого» вида, подобранного владелец сайтаом | средняя / средний | лаборатория с ползунками GPU-пути рядом со старым SVG, подбор заново |
| R9 | Энергосбережение iOS ограничивает rAF 30 Гц, `auto` уходит в `frost` по ошибке | средняя / низкий | порог от фактической частоты |
| R10 | Стекло над краем фото: выборка за границей текстуры (`CLAMP_TO_EDGE` размазывает край) | высокая на выходе из героя / низкий | переход в `frost` чуть раньше, чем кромка дойдёт до края фото (IntersectionObserver с запасом ~maxShift) |
| R11 | Шейдер на старых мобильных GPU: `highp` во фрагментном шейдере, `pow` с отрицательной степенью около 0 | низкая / низкий | ограничения `x ≥ 0,002`, `max(length, 1e-4)`; тест на старом Android |
| R12 | В WebKit что-то поведёт себя иначе, чем в Chrome (как было с SVG) | неизвестно | первый же прототип — в настоящем Safari и на iPhone, не в Playwright |

## 13. План проверки (что делать первым)

Всё в `glass-rnd/`, сайт не трогаем.

1. **Прототип `glass-rnd/proto/gpu-header.html`** (~300 строк, без сборки): копия героя с одним
   слайдом и полосатой линейкой поверх, липкая капсула с canvas, шейдер из 4.8. Переключатели
   `?mode=gpu|svg|frost`, `?k=1|3|5`, `?predict=1`, встроенный зонд кадров и отставания
   (performance.md 6.2). Отдавать `python3 -I -m http.server` и открывать **в настоящем Safari**
   (Mac) и на iPhone по локальной сети.
2. Замеры: худший кадр и p95 при прокрутке (gpu против svg против frost); отставание линзы —
   запись экрана 120/240 fps; смена слайда с заливкой заранее и без неё.
3. Визуальная сверка: центр линзы совпадает с фото (решётка, цвет); кромка без ступенек; вид в
   Safari = Chrome = Firefox.
4. Лаборатория: ползунки `bevel/thickness/gap/ior/dispersion/frost/rim/specular` рядом со старыми,
   владелец сайта подбирает пресеты `bar/pill/dot`.
5. Только после этого — `plugin/liquid-glass.js` + `liquid-glass.css` + `сайт-пример-glass.js` в
   `glass-rnd/site-next/` с отчётом «было/стало».
