# Архитектура «свободная»: стекло-кольцо на WebGL2 поверх живого матового стекла

Дата: 30.10.2026. Черновик проекта, кода нет. Собран из всех файлов `research/*.md` и нескольких
дополнительных источников (ссылки по тексту).

Метки:
- **[S27]** — проверено в настоящем Safari 27 (из `CONTEXT.md`);
- **[ист.]** — по источникам, нами не проверено;
- **[?]** — гипотеза или оценка, **требует проверки в настоящем Safari / на iPhone**;
- Playwright-WebKit доказательством не считаем.

## 0. Идея в трёх строках

1. **Середину стекла рисует браузер, кромку рисуем мы.** Под стеклом лежит обычный
   `backdrop-filter: blur() saturate()`. Его считает видеокарта во всех движках, и он идёт синхронно
   с прокруткой, потому что его ведёт композитор. Поверх него маленький WebGL2-canvas рисует
   **только кольцо кромки**: преломление, аберрацию, френелевскую кромку и блик. В середине canvas
   прозрачный.
2. **Картинку за стеклом шейдер берёт как текстуру из самого `<img>`/`<video>`**, а не из копии DOM.
   SVG-фильтров на пути нет вообще. Значит, процессорный путь Safari, `feImage`, `userSpaceOnUse`,
   `sRGB` и грабли с композитными слоями нас не касаются.
3. **Где картинки под стеклом нет** (текст, карточки), там Regular-матовое, как у Apple. Исключение —
   Chromium: там при желании включается живое SVG-преломление через `backdrop-filter: url()`.

Почему именно так, а не «вся линза в WebGL», как советуют `graphics.md` и `performance.md`. Главная
нерешённая беда любого стекла, которое двигает JS, — **отставание от прокрутки**. Прокрутку двигает
композитор, а JS узнаёт о новом положении на кадр позже
([Mozilla: scroll-linked effects](https://firefox-source-docs.mozilla.org/performance/scroll-linked_effects.html),
[WebKit bug 206228](https://bugs.webkit.org/show_bug.cgi?id=206228),
[заметки WebKit о прокрутке на macOS](https://trac.webkit.org/wiki/WhatsChangingwithscrollingonmacOS),
[w3c/svgwg#1142](https://github.com/w3c/svgwg/issues/1142)). Если WebGL рисует всю линзу, то
отставший на кадр кусок фото виден в чистой середине капсулы, где глаз сравнивает его с фото рядом.
При 1500 px/с это ~25 px за кадр 60 Гц. Если WebGL рисует только кромку, отставание остаётся там, где
картинка и так сжата и изогнута, а середина берёт фото у композитора и не отстаёт никогда. Это и
дешевле: шейдер красит не всю капсулу, а 30–50 % её площади.

У других реализаций такого разделения я не нашёл: все рисуют линзу целиком одним способом
(`implementations.md`, разделы 1–16).

## 1. Слои одного стеклянного элемента

```
  .lg (хост: ваш элемент, например .nav__row)        position: relative; isolation: isolate
  ├─ ::before  «оболочка»   z -2   CSS: тень, тон, запасная кромка (inset box-shadow)
  ├─ .lg-back  «середина»   z -1   backdrop-filter: blur(r) saturate(s)   ← GPU, синхронно с прокруткой
  ├─ canvas.lg-ring «кольцо» z -1  WebGL2: преломление/аберрация/блик только у кромки, aria-hidden
  └─ содержимое хоста (текст, ссылки, кнопки) — живой DOM поверх всего
```

- Все слои лежат внутри хоста и **не двигаются относительно него**. Шапка `position: sticky`, её ведёт
  композитор, поэтому форма стекла, кромка, тень и текст неподвижны и не дрожат. Внутри canvas при
  прокрутке меняется только картинка.
- Слой `.lg-back` — то же матовое стекло, что на сайте сейчас (`backdrop-filter: blur(20px)
  saturate(1.8)`, `page.css` строка 49). Для варианта Clear размытие меньше (2–4 px). Это уже
  проверенный и быстрый путь во всех движках [S27 для матового на сайте].
- Каждый слой отключается независимо. Нет WebGL — остаются оболочка и середина, получается матовое
  стекло. «Уменьшить прозрачность» — остаётся одна оболочка с плотной заливкой. Это и есть
  деградация без поломки: на любом шаге пользователь видит законченное стекло, а не дыру.
- Правило из `CONTEXT.md` про `translate3d`/`will-change` внутри фильтра здесь не действует: SVG-фильтра
  нет. Canvas — обычный композитный слой, хост можно анимировать как угодно.
- Safari 26 красит свои панели по фону fixed/sticky элементов у края экрана
  ([1ar.io](https://1ar.io/updates/safari-26-liquid-glass-web/), `fresh.md` 3.3). Поэтому у хоста
  фон прозрачный, а матовость сидит на дочернем `.lg-back` с `aria-hidden` [?, проверить на iPhone].

## 2. API

### 2.1 Подключение (статика, без CDN)

```
site/assets/lglass/
  lglass.js        ~6–8 КБ min+gz: ядро, выбор режима, CSS-оболочка, наблюдатели
  lglass-gl.js     ~4–5 КБ min+gz: WebGL2-кольцо, грузится лениво через import()
  lglass.css       ~1,5 КБ: оболочка, матовый слой, медиазапросы доступности
```
Без зависимостей: three.js (~150 КБ gz) ради одного квадрата не нужен (`graphics.md` 2.3). Чужой код
не копируем. Формулы взяты из открытых разборов: kube.io, Inigo Quilez, Grassi, m2-md (MIT).

### 2.2 Декларативно (разметка)

```html
<link rel="stylesheet" href="/assets/lglass/lglass.css">
<script type="module" src="/assets/lglass/lglass.js"></script>

<!-- шапка: стекло над фото первого экрана -->
<div class="nav__row" data-lglass="clear" data-lglass-over=".hero__photo"
     data-lglass-preset="bar"></div>

<!-- кнопка ▶ над видео -->
<button class="video__btn" data-lglass="clear" data-lglass-over="video" data-lglass-preset="dot">

<!-- плашка над текстом: будет Regular-матовое -->
<div class="note" data-lglass="regular"></div>
```
`lglass.js` при загрузке находит `[data-lglass]` и вызывает для каждого `glass(el, opts)`. Атрибуты
`data-lglass-*` повторяют параметры из 2.3.

### 2.3 Программно

```js
import { glass, glassConfig } from '/assets/lglass/lglass.js';

const g = glass(document.querySelector('.nav__row'), {
  variant: 'clear',            // 'clear' (над медиа) | 'regular' (над текстом) — как у Apple
  over: '.hero__photo',        // что под стеклом: селектор | <img> | <video> | <canvas> | контейнер со слайдами | null
  shape: 'auto',               // 'auto' = border-radius хоста; или { radius: 30, squircle: 4 }
  // оптика (в CSS-пикселях, не зависят от DPR):
  rim: 14,                     // ширина кромки, где идёт преломление
  bend: 1.0,                   // сила изгиба (масштаб профиля кромки)
  ior: 1.5,                    // показатель преломления
  thickness: 22,               // «толщина» стекла: сколько px сдвига даёт полный наклон
  profile: 'squircle',         // 'squircle' | 'circle' | 'lip' (у переключателей)
  dispersion: 0.12,            // аберрация: разница сдвига между красным и синим (доля)
  samples: 'auto',             // 1 | 3 | 5 спектральных выборок; 'auto' по движку и замеру
  frost: 3,                    // размытие середины (px), backdrop-filter
  saturate: 1.6,
  tint: 'rgb(255 255 255 / .26)', // тон заливки
  light: { angle: -60, strength: .7, back: .25 }, // блик: направление, сила, отражение напротив
  rimLight: .4,                // френелевская светлая кромка
  shadow: .7,                  // тень (CSS)
  tone: 'auto',                // 'auto' | 'light' | 'dark': переключать светлое/тёмное стекло по фону
  quality: 'auto',             // 'auto' | 'high' | 'low' | 'css' (принудительно без WebGL)
  sync: 'ring',                // 'ring' (по умолчанию) | 'full' (вся линза в WebGL, для опытов)
});

g.set({ bend: .8 });           // поменять параметры на лету (без пересборки, это uniform'ы)
g.source(img, { fade: 900 });  // сменить картинку под стеклом с кроссфейдом
g.refresh();                   // пересчитать геометрию (обычно не нужно: ResizeObserver)
g.mode;                        // 'ring' | 'frost' | 'solid' | 'off' — что сейчас рисуется
g.on('mode', m => …);          // событие смены режима (для отладки и лаборатории)
g.destroy();

glassConfig({ debug: false, maxDpr: 2, governor: true }); // общие настройки страницы
```

Пресеты (`bar`, `dot`, `pill`, `card`) — это наборы параметров, подобранные владелец сайтаом в лаборатории
(`CONTEXT.md`: капсула rim 4.5 / bend −140 / spread .12 / soft 1.3; кнопки rim 8 / bend −40 …).
Единицы другие: старые `bend`/`spread` были силой feDisplacementMap, новые — физические. Перевод
подбирается один раз в лаборатории на глаз, по общему снимку «до/после» [?].

### 2.4 Слайды первого экрана

`over: '.hero__photo'` — это контейнер со стопкой `<img>`. Плагин следит за классом `.is-on` через
`MutationObserver` на атрибут `class` (без завязки на событие `slide` из `site.js`) и при смене сам
вызывает `source(новая, { fade: длительность transition из computed style })`. Длительность и кривую
берёт из `getComputedStyle(img).transition*`, поэтому кромка проявляется в такт с фото. При
`prefers-reduced-motion` переход мгновенный.

## 3. Откуда берётся картинка за стеклом

| Что под стеклом | Источник для шейдера | Когда обновляется |
|---|---|---|
| `<img>` своего домена (слайды героя) | `texImage2D(img)` после `await img.decode()`; лучше отдельная маленькая копия `data-lglass-src` (768 px по ширине, webp из `build.py`) | один раз на слайд, + `generateMipmap` |
| два слайда во время смены | две текстуры, `mix(texA, texB, t)` в шейдере | t по времени от начала перехода |
| `<video>` | `texImage2D(video)` в `requestVideoFrameCallback`, только пока кнопка видна; на iPhone — постер или кадр раз в N кадров [?] | на новом кадре видео |
| `<canvas>` | текстура из canvas | по событию автора |
| живой DOM (текст, карточки) | **нет текстуры**: Regular-матовое. В Chromium по желанию — `backdrop-filter: url(#map)` (раздел 9) | — |

**Геометрия без чтения раскладки на каждом кадре.** На старте и в `ResizeObserver` (хост, контейнер
`over`, `<html>`) плагин один раз считает:
- прямоугольник фото в координатах документа (`getBoundingClientRect() + scrollY`);
- отображение «пиксель экрана → UV текстуры» с учётом `object-fit: cover` и `object-position`
  (из `naturalWidth/Height` и computed style). У нас `cover` без transform (`page.css` 72, 422);
- прямоугольник хоста **во вьюпорте** (шапка sticky, `top` постоянный, пока она прилипла).

В кадре нужен только `scrollY`: `uvRect = константа − scrollY · k`. Никаких
`getBoundingClientRect()` при прокрутке, никакого принудительного layout (аудит G6).

**Компенсация отставания (новое, [?]).** Кольцо всё равно рисуется по `scrollY` с задержкой на кадр.
Чтобы эту задержку не было видно даже в кромке:
1. **Упреждение.** Скорость прокрутки сглаживаем (EMA по последним 3–4 событиям `scroll`) и рисуем
   кадр по `scrollY + v·τ`, где τ ≈ 1 период кадра. На `scrollend` (Safari 26.2+
   [ист.](https://www.infoq.com/news/2026/04/safari-scrollend-support)) рисуем точное положение.
   Упреждение ограничено краями страницы, а при резкой смене знака скорости сбрасывается.
   Величину τ подбирать по видео 240 fps в настоящем Safari.
2. **Размытие по скорости.** В шейдере `lod += k·|v|`, плюс выборки растянуты вдоль оси прокрутки.
   При быстрой прокрутке кромка становится мягче, и остаток рассинхрона в ней исчезает. Физически это
   выглядит как смаз в движении, поэтому неестественно не смотрится. При «Уменьшить движение» выключено.
3. **Мягкий внутренний край кольца.** У внутренней границы кольца сдвиг стремится к нулю (профиль
   squircle, раздел 4), а альфа canvas плавно падает до нуля на 4–6 px. Шва между «нашим» и «браузерным»
   фото нет, а на быстрой прокрутке там видно только лёгкое двоение.

Для сравнения в лаборатории остаётся режим `sync: 'full'`: вся линза в WebGL, как у liquidGL.
Выбирать по записи экрана, а не на вкус.

## 4. Как считается преломление

Всё аналитически в фрагментном шейдере (GLSL ES 3.0), без карт и без предрасчёта.

1. **Форма.** SDF скруглённого прямоугольника по Inigo Quilez
   ([2D distance functions](https://iquilezles.org/articles/distfunctions2d/)). Норма L4 вместо
   евклидовой в углах даёт squircle с непрерывной кривизной, как у Apple
   ([Grassi](https://charlesgrassi.dev/blog/apple-liquid-glass/)). Радиус берём из `border-radius`
   хоста, у капсулы это половина высоты. `d < 0` внутри.
2. **Где кольцо.** `x = clamp(-d / rim, 0, 1)`: 0 на краю, 1 там, где кромка переходит в плоскую
   середину. При `x = 1` фрагмент отбрасывается (`discard`), canvas там прозрачный. Дополнительно
   рисуем не один квадрат, а **рамку из 4 полос** (8 треугольников) вокруг середины. Тогда GPU вообще
   не запускает шейдер для середины.
3. **Профиль высоты кромки.** Выпуклый squircle `h(x) = ⁴√(1 − (1 − x)⁴)` по
   [kube.io](https://kube.io/blog/liquid-glass-css-svg/): мягкий переход к плоскости и тонкая на вид
   кромка. Вогнутые профили не берём, они уводят лучи за край. Профиль `lip` — для переключателей.
4. **Нормаль.** `n = normalize(vec3(−∇d · h′(x) · bend, 1))`. Градиент SDF считаем аналитически, а не
   через `dFdx`, чтобы не было ступенек в углах.
5. **Сдвиг.** Закон Снеллиуса: `r = refract(vec3(0,0,−1), n, 1/ior)`,
   `offset = r.xy / −r.z · thickness`. В плоской середине `n = (0,0,1)`, и сдвиг нулевой. Это
   «Pixel Normal Offset» из Unreal
   ([Epic](https://dev.epicgames.com/documentation/unreal-engine/refraction-using-pixel-normal-offset-in-unreal-engine)),
   именно так ведёт себя Apple: середина чистая, у края фон затягивает за кромку.
6. **Выборка.** `textureLod(tex, uv(p + offset), lod)`. Здесь `lod` = размытие середины (чтобы стык
   с `backdrop-filter` совпадал по мягкости) + размытие по скорости (раздел 3). Mip-карты делаются один
   раз на слайд, так что размытие почти даром. Выход за край картинки — `CLAMP_TO_EDGE`. Шапка у верха
   фото: картинку на 4 % «дотягиваем» отражением (`MIRRORED_REPEAT`), чтобы у верхней кромки не было
   полосы одного цвета.

Почему не готовая карта смещения, как у kube.io и Aave. Карта нужна только SVG-фильтру. В шейдере та же
формула стоит десяток операций на пиксель, а смена формы, радиуса или `bend` становится просто новым
uniform, без пересборки.

## 5. Аберрация

Спектральная развёртка, а не три резких контура R/G/B
([m2-md](https://github.com/m2-md/liquid-glass-refraction-shader/blob/main/README.md):
1/3/8 выборок стоят 0,131/0,164/0,217 мс GPU на M2 Pro).

```
for i in 0..N-1:  w = i/(N-1)                 // 0 = красный край, 1 = фиолетовый
  off_i = offset · (1 + dispersion · (w − .5))
  col  += spectrumWeight(w) · textureLod(tex, uv(p + off_i), lod).rgb
col /= Σ spectrumWeight                          // веса нормированы, белое остаётся белым
```
- `N = 3` по умолчанию, `5` в режиме `high` на Mac. При `dispersion < 0.03` `N = 1`: аберрации не видно,
  тратить выборки незачем (аудит G5).
- Аберрация растёт сама собой там, где больше сдвиг, то есть у самого края. В середине её нет. Это
  совпадает с Apple: у них она едва заметна, отдельного слова «aberration» в материалах нет (`apple.md` 1).
- Для сайт-пример с их оптикой это, пожалуй, самый «правильный» ход: мягкая радужная кайма, как у
  настоящей линзы, без трёх резких контуров.

## 6. Блик и светлая кромка

В шейдере, потому что тогда они точно совпадают с геометрией преломления:
- **Френель (Шлик)**: `F = 0.04 + 0.96·(1 − n.z)^5`, `col = mix(col, white, F · rimLight)`. У края
  кромка светлеет сама, без «кромки 40 %» на глаз.
- **Направленный блик**: `spec = pow(max(dot(n, L), 0), 24) · strength`, `L` из `light.angle`
  (по умолчанию сверху-слева, −60° как у kube.io). С противоположной стороны тот же расчёт с `−L` и
  весом `back` (0,25) — тусклое отражение снизу-справа.
- **Подвижность** (по желанию): угол `L` следует за курсором на десктопе, через uniform, без
  пересборки. На iPhone гироскоп не берём: нужен запрос разрешения. При «Уменьшить движение» угол
  постоянный.

Когда WebGL нет, оболочка `::before` рисует ту же кромку через CSS: три `inset box-shadow` и градиент
сверху (как сейчас `.is-glass::before`, `page.css` 393, аудит C6). В режиме `ring` CSS-кромка
выключается, чтобы не было двух кромок.

## 7. Тень, тон, светлое/тёмное

- **Тень** — `box-shadow` хоста: `0 10px 30px -14px rgb(0 0 0 / calc(.45·shadow))` и короткая
  контактная тень. Никаких фильтров. Над фото сильнее, над белым слабее: класс по тону (ниже).
- **Тон** — полупрозрачная заливка `tint` на `.lg-back` (общая для середины и кольца, поэтому стыка нет)
  плюс `saturate`.
- **Светлое/тёмное по фону**, как мелкие элементы у Apple (`apple.md` 7). Яркость полосы фото под
  шапкой считает заранее `build.py` и пишет в `data-lglass-tone="0.41 0.38 …"` у каждого `<img>`
  (8–10 чисел по высоте кадра, аудит G7/S3). Плагин выбирает число по положению шапки и переключает
  `lg--on-dark`/`lg--on-light` с гистерезисом 0,42/0,58 (как в нынешнем `glass.js`). Если данных нет —
  один раз уменьшает картинку до 1×8 в canvas при смене слайда, не на кадре.
- **Clear над фото**: локальное затемнение около 35 % только под текстом (радиальный градиент на
  `.lg-back`), как советует HIG (`apple.md` 6).

## 8. Выбор режима и «регулятор качества»

### 8.1 Лестница режимов

```
ring-high  → ring (N=3) → ring-low (N=1, DPR 1, без размытия по скорости) → frost → solid → off
```
- **Стартовый режим** выбирается по признакам, а не по UA: есть ли WebGL2 (`canvas.getContext('webgl2')`
  с `failIfMajorPerformanceCaveat: true`), есть ли `backdrop-filter`, медиазапросы доступности, тип
  `over`. Движок WebKit для мелких поправок — по `'webkitConvertPointFromNodeToPage' in window`
  (приём Amir-Abushanab, `implementations.md` 5).
- **Регулятор (governor)**. Первые 2 секунды прокрутки над фото плагин меряет интервалы rAF (тот же
  зонд, что в `performance.md` 6.2). Если p95 > 1,25 периода или есть кадр > 50 мс, режим опускается на
  ступень. Наверх не поднимается до перезагрузки, чтобы не было качелей. Решение запоминается в
  `sessionStorage` (в `try/catch`). Пороги — из `performance.md` 6.5.
- **Потеря контекста** (`webglcontextlost`) → `frost`, без попыток воскресить на ходу. Восстановление —
  по `webglcontextrestored`.
- **Видимость.** `IntersectionObserver` на контейнер `over` с `rootMargin`, равным высоте шапки. Фото
  ушло из-под стекла → canvas `hidden`, слушатель `scroll` снят, контекст остаётся. Вкладка скрыта —
  всё стоит. Ленивая инициализация: контекст и текстуры создаются при первом пересечении.

### 8.2 Один контекст на страницу

У браузеров лимит около 16 WebGL-контекстов (`performance.md` 5.3). Плагин держит **один** контекст
на `OffscreenCanvas` (WebGL на главном потоке, Safari 17+ [ист.]) и для каждого стекла рисует его кольцо,
потом `transferToImageBitmap()` → `bitmaprenderer`-контекст canvas'а этого стекла. Передача без копии,
по [MDN](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas) это штатный приём
«один WebGL — много canvas». `ImageBitmapRenderingContext` в Safari есть с 11.1
([MDN](https://developer.mozilla.org/en-US/docs/Web/API/ImageBitmapRenderingContext/transferFromImageBitmap)).
Есть известное расхождение Chrome/Safari со спецификацией по размерам такого canvas
([whatwg/html#7833](https://github.com/whatwg/html/issues/7833)), поэтому `width`/`height` ставим явно
[?]. Запасной путь, если на каком-то движке это сломается: у шапки свой обычный WebGL2-canvas, у
кнопок ▶ свои (их 3–5, в лимит укладываемся).

## 9. Отдельная ветка для Chromium (по желанию, не основа)

Только Chrome, Edge, Samsung Internet: `backdrop-filter: url(#lg-map)` на `.lg-back` с картой смещения
из того же расчёта, что в шейдере. Карту один раз рисует canvas, подаётся через `feImage`
(`color-interpolation-filters="sRGB"`, альфа карты 255 —
[emit-solution](https://emit-solution.com/en/blog/recreate-apple-liquid-glass-css)). Этот путь
преломляет **живой DOM** (текст, карточки), синхронно с прокруткой и на GPU. Нужен там, где под
стеклом не картинка: плашки над текстом, фильтр каталога. Определять только по движку: Firefox и Safari
`backdrop-filter: url()` парсят, но не рисуют, а `@supports` отвечает «да» (`browsers.md` 2).
Firefox-бонус `-moz-element()` не беру: риск удаления функции, а пользы мало.

## 11. Ожидаемая скорость

Все цифры ниже — **оценки, не замеры** [?]. Опорные данные — m2-md (WebGL2-стекло 960×540 на M2 Pro:
0,16 мс GPU) и наши замеры SVG.

| | Mac (Apple Silicon), Safari / Chrome | iPhone 13–16, Safari |
|---|---|---|
| Пикселей в кольце шапки | капсула ~1100×60 CSS, DPR 2 → 0,26 Мп всего, кольцо ~40 % → **~0,1 Мп** | ~360×56 CSS, DPR ограничен 2 (вместо 3) → 0,08 Мп, кольцо → **~0,04 Мп** |
| GPU на кадр | ~0,05–0,1 мс (N=3) | ~0,2–0,6 мс (GPU слабее в 5–10 раз) |
| CPU (главный поток) на кадр | ~0,1 мс: uniform'ы + draw + `transferToImageBitmap` | ~0,2–0,3 мс |
| `backdrop-filter` середины | как сейчас у матового (GPU) | как сейчас у матового |
| Смена слайда | `decode()` + `texImage2D` 768 px + mip: ~2–5 мс **один раз**, вне перехода; сам переход — uniform | ~5–10 мс один раз; переход — uniform |
| Память | текстуры 2 × 768×512 × 4 × 1,33 ≈ 4 МБ + canvas ~0,5 МБ | то же (≈ 4,5 МБ) против ~35 МБ временных буферов SVG (`performance.md` 5.6) |
| Ожидаемый итог при прокрутке | 60 fps в Safari (rAF там ~60 Гц), 120 в Chrome; худший кадр — как у матового (~10 мс) | 60 fps; худший кадр ≤ 17 мс |

Для сравнения: нынешний SVG-фильтр в Safari пересчитывает ~0,56–0,83 Мп на каждом из ~17 проходов на
CPU (≈ 10 Мп-операций на кадр), худший кадр 33 мс [S27]. Кольцо — это ~0,1 Мп на GPU в одном проходе.
Разница должна быть на два порядка. Подтвердить можно только замером в настоящем Safari.

## 12. Риски и как их закрываем

| Риск | Вероятность | Что делаем |
|---|---|---|
| **Стык середины и кольца виден** (разное размытие/цвет `backdrop-filter` и шейдера, разные цветовые пространства) | средняя | `lod` подобрать под радиус `backdrop-filter`; тон — общий слой; мягкий внутренний край 4–6 px. Проверка на полосатой решётке под стеклом. Если стык не уходит — режим `sync:'full'` с упреждением |
| **Отставание кольца на быстрой прокрутке** | средняя | упреждение + размытие по скорости (раздел 3). Мерить видео 240 fps в Safari и на iPhone |
| `backdrop-filter` + canvas-потомок в одном хосте ведут себя в Safari неожиданно (порядок слоёв, backdrop root) | низкая–средняя [?] | первый же A/B в настоящем Safari; запасной вариант — canvas сосед хоста, а не потомок |
| iOS 26: fixed/sticky элементы прыгают на ~10 px при сворачивании адресной строки ([WebKit 297779](https://bugs.webkit.org/show_bug.cgi?id=297779), по отчётам частично исправлено в 26.1) | средняя | геометрию брать из `visualViewport` и пересчитывать на его `resize`/`scroll`; это и сейчас бьёт по шапке |
| `OffscreenCanvas` + `bitmaprenderer` с багами размеров в WebKit ([whatwg/html#7833](https://github.com/whatwg/html/issues/7833)) | низкая [?] | явные размеры; запасной путь — отдельные WebGL-canvas |
| `texImage2D(video)` медленный в Safari, были регрессии ×20 ([WebKit 236699](https://bugs.webkit.org/show_bug.cgi?id=236699)) | высокая для iPhone | на iPhone — постер или кадр раз в 4–8 кадров видео; живое видео только по замеру |
| Слабые Android, GPU-драйверы | средняя | `failIfMajorPerformanceCaveat`, регулятор качества, DPR 1 |
| Safari «Уменьшить прозрачность» не видна из веба | точно есть | ручной выключатель; стекло не служит фоном, без которого текст не читается (затемнение 35 % под надписями) |
| Потеря WebGL-контекста при нехватке памяти на iOS | низкая | маленькие текстуры, один контекст, `frost` при потере |
| Картинки с чужого домена | у нас нет | `crossorigin`; иначе `frost` |
| Пресеты владелец сайтаа не переносятся 1:1 (другие единицы) | точно | одна сессия в лаборатории: старое и новое стекло рядом на одном фото |
| Спрос «стекло над любым DOM» в Safari | — | честного пути нет ни у кого, пока WebKit не выпустит `backdrop-filter: url()` (PR 68614, и он тоже программный, `fresh.md` 4). Regular-матовое — это и логика Apple |

1. **Прототип «кольцо» в лаборатории** `glass-rnd/` (не на сайте): шапка над одним фото. В настоящем
   Safari Mac: стык середины и кольца на решётке, худший кадр прокрутки, видео 240 fps для отставания.

## 14. Почему этот вариант, а не другие

| Подход | Плюс | Почему не основа |
|---|---|---|
| Нынешний SVG по копии | работает в Safari [S27] | CPU в Safari и Firefox, 17 проходов, отстаёт, на iPhone «очень плохо» |
| Урезанный SVG (поля, 1 проход, карта в SourceGraphic) | в 3–8 раз дешевле [?] | всё равно CPU и отставание, разный вид по движкам; годится как промежуточная правка сайта |
| Вся линза в WebGL | дёшево, одинаково везде | отставание видно в чистой середине |
| Снимок DOM в текстуру (liquidGL, ybouane) | стекло над чем угодно | 100–500 мс на снимок, статично, foreignObject в Safari ненадёжен |
| HTML-in-Canvas | живой DOM в шейдере | только Chrome за origin trial |
| `backdrop-filter: url()` | живой DOM, GPU, синхронно | только Chromium |
| **Кольцо WebGL + матовая середина (этот проект)** | GPU во всех движках, середина синхронна с прокруткой, один вид везде, деградация по слоям | работает только над картинкой или видео; стык и отставание кольца — проверить |
